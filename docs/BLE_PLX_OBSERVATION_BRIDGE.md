# BLE PLX observation bridge: offline preparation only

Verified 7 November 2026 against the existing research pin. No native scan, connection, radio action, native build, physical reception or hardware compatibility test was performed. `packages/core/ble-plx-observation.ts` adds no runtime dependency and is not imported by the native scanner. The offline workbench now uses it through the separately reviewed selected-source evidence replay path.

## API and representation contract

`prepareBlePlxObservation(platform, deviceFields, provenance)` accepts a real Device-shaped object or a synthetic/read-only copy. It never calls Device methods. Selected own data properties are copied; accessors on selected fields are rejected. Device methods, manager handles, MTU and unrelated extra properties are intentionally not retained. Inputs should be ordinary trusted SDK objects or parsed JSON, not executable proxy objects.

The result contains a bounded defensive `snapshot`, `unavailableFields`, source provenance, a `retentionWarning`, and a derived `document`/`observation`:

- Android uses **only** `rawScanRecord` for AD parsing. It retains exact decoded bytes including padding, unknown/repeated AD and malformed tails. It does not reconstruct raw bytes from normalized fields. Completeness is always `unknown`, even when parsing succeeds. If raw data is null/missing, status is `raw-scan-record-unavailable` and document/observation are null. An explicitly supplied empty base64 string remains distinguishable from unavailable data.
- iOS uses the exposed normalized fields for the existing `ios-advertisement-fields` document. The original `rawScanRecord` value is bounded/validated base64 and retained opaquely in the snapshot, never parsed as AD bytes or used to override fields. It is not verified to be JSON or consistent with the normalized fields. No raw advertisement is invented. Capture completeness remains `not-exposed`.
- `localName` is not filled from `name`: the latter may be a cached peripheral name. Manufacturer bytes are not stripped or prepended. Service payloads are not prepended with UUID bytes. UUID spelling/case and original base64 strings are retained in the snapshot; the existing decoder canonicalizes UUIDs in its interpretation.
- Missing/undefined properties become null in the selected snapshot and are additionally listed in `unavailableFields`; explicit null is not listed. Null dictionaries/lists and empty dictionaries/lists remain distinct there. The existing offline projection uses empty arrays for unavailable iOS service collections, so it cannot preserve that distinction alone.
- Source RSSI 127 is retained but projected to unavailable/null. TX power uses SDK null/missing for unavailable. The pinned Android parser reads a signed AD octet directly; it does not use Android ScanRecord.getTxPowerLevel or its Integer.MIN_VALUE sentinel. TX -128 and Integer.MIN_VALUE are rejected as outside the existing importer range, not silently assigned an undocumented SDK sentinel meaning. Other out-of-range/noninteger metrics are rejected, not silently clamped. No signal-strength or name heuristic establishes identity, range, authenticity or sensor truth.
- No SDK source timestamp is exposed in the inspected mapping. The caller must supply a source label and source timestamp under the existing recorded-import contract, identifying callback receipt time when that is what it is. Never fill it with adapter/import time or present it as hardware transmission time. Synthetic fixtures require null capturedAt. This adapter adds no live/native provenance category; physical reception and authenticated identity remain false.

## Bounds and retention

Base64 uses the standard RFC 4648 alphabet with required padding and zero pad bits; whitespace, URL-safe alphabet, partial quartets, noncanonical pad bits and oversize input fail. Empty strings are valid encodings. Binary AD/service/manufacturer values are each at most 1650 decoded bytes. iOS opaque JSON base64 is at most 8192 decoded bytes. Each UUID collection/service dictionary is limited to 32 entries; normalized payload and resulting document must also pass existing aggregate importer bounds. Selected snapshots are limited to 16384 JSON UTF-16 characters. Strings are bounded; values are never truncated to fit.

**The snapshot is preparation output, not an evidence record.** Existing `prepareBleEvidenceInput(result.document)` saves only the derived document, subject to its smaller 4096-character limit. It does not retain the snapshot, original base64 spelling, identifier, cached name, overflow/solicited UUIDs, Android normalized copies, iOS opaque JSON, or null/missing/empty distinctions. Android decoded raw bytes remain exact in advertisingHex, and iOS selected decoded service/manufacturer bytes remain exact in the projection. The separately reviewed `analysis.ble-source` schema and replay path now retain the complete selected snapshot with provenance; see `BLE_PLX_SOURCE_EVIDENCE.md`. Legacy projection saves are not silently upgraded. Callers must show the returned retention warning before presenting projection-only retention as complete capture evidence.

## Tests and remaining gate

`node --test tests/ble-plx-observation.test.ts` covers Android/iOS-shaped **synthetic** records, Android malformed/repeated/unknown AD and padding, iOS base64 JSON separation, null/missing/empty fields, sentinel metrics, exact selected payloads, defensive copying, canonical base64 for every length 0–1650 and exhaustive one-/two-byte tails plus nonzero pad-bit variants, invalid pad bits/alphabet/size, aggregate limits, duplicate canonical UUIDs and source time validation. Node Buffer is used only by tests as an independent encoding oracle; runtime code is dependency-free ECMAScript.

`node tools/demo-phone-ble.ts` runs Android and iOS SDK-shaped synthetic BTHome battery observations through the adapter, existing decoder and evidence preparation/replay. It prints format interpretation, source provenance, false verification flags and the projection-retention warning. It does not save evidence, scan or call a provider.

Actual collection remains unchanged: `src/platform/bluetooth.native.ts` scans only the custom AXP service, returns only accessory ID/name/RSSI, and does not call this adapter. Existing `app.json` sets `neverForLocation: true`, which can filter beacons. General sensor/beacon compatibility therefore cannot be inferred from this bridge. Follow the controlled owned-device experiment in `BLE_OFFLINE_EXPERIMENT.md` before any native collector integration or physical reception claim. Source-time semantics, permission/filter state, phone/OS/build details and snapshot retention need explicit design before enabling capture.
