# USB JavaScript lifecycle fixtures

Scope: synthetic `ApexNative` boundary fixtures only. No native module, Android permission prompt, device, Kotlin compilation, or native acceptance test was run. Kotlin is unchanged.

The retained baseline log runs six regression cases against commit `9436307`; all six fail. The complete enhanced suite runs against the repaired JavaScript transport. The first attempted unbounded baseline run stalled on its competing pending permission fixture and was interrupted; its four original passing cases are not evidence of race coverage. The retained focused baseline excludes that hung case.

The transport now reserves one lease per native object before permission/open, rejects competing instances, waits acquisition settlement during cancellation, closes a known token, and preserves that token for explicit disconnect retry after close failure. A close failure permanently marks the lease uncertain: even a fulfilled retry may be a native no-op and cannot release the fence. Permission refusal or listener installation failure before invoking open can release ownership. After invoking open, rejection or an invalid token leaves ownership uncertain and fenced. Calling disconnect cannot repair unknown-token ownership and reports this explicitly; there is no invented reset, permission retry, or timeout-based release.

A bounded early terminal-event buffer prevents early closure from being lost while open resolves. Terminal overflow fails closed and requires known-token cleanup. Queued and active JavaScript write promises reject on cancellation; the lease still waits for outstanding native write settlement. Callback exceptions cannot release ownership; removed callbacks are generation-fenced, and listener removals are attempted once.

Native source review only: `openLink` installs the link and starts its reader before returning the token. `closeLink` clears its link field before physical interface/connection cleanup; exceptions can prevent the terminal event. This supports conservative uncertainty handling but does not establish actual bridge ordering, driver cleanup, or hardware safety. A successful native close or matching terminal event is the existing boundary signal, not independent proof of physical release. Hung permission/open/write/close promises may retain the lease indefinitely. Separate wrappers around the same native module object are fenced; independently instantiated native module objects are not proven equivalent.

Integration requirement: App must retain a failed session handle if cleanup fails, so explicit Disconnect can retry known-token cleanup and surface retained uncertainty. A fulfilled retry after failure does not prove release. `DeviceSession.close()` already calls transport disconnect even for a closed session. Its open failure path suppresses cleanup errors, so the App must not interpret the original open failure as proof of successful cleanup. Unknown-token ownership remains blocked even with a retained handle.

Independent adversarial review caught delayed-terminal, delayed-write terminal-release, and matching-early-terminal overflow escape paths in the initial repair. The retained review logs record those failures. Sticky explicit-close intent and failed-close uncertainty now prohibit autonomous release; early buffer overflow also prohibits terminal release. Null native events and sparse byte arrays are rejected. These are JavaScript guarantees only, not a native cleanup acknowledgement protocol.

Explicit retry after a rejected close may attempt the same token but cannot restore reuse in this source-only patch, even if the underlying retry fulfills. A source-order regression models `link = null` followed by physical-close failure, then a fulfilled no-op retry; ownership remains fenced. This differs from ordinary successful first close or terminal teardown without an explicit-close failure, which can release normally after required promise settlement. Retaining the App handle permits attempted cleanup and honest error reporting, not guaranteed recovery.

Write-lifetime follow-up: USB writes accept only fixed-buffer Uint8Array inputs of 1 through MAX_FRAME (524) bytes. Intrinsic view/buffer accessors check the real byte extent before allocation; fresh built-in views snapshot caller bytes without caller iterator/slice hooks. Shared/resizable/detached buffers and non-byte views are refused. This is input validation, not an arbitrary JavaScript sandbox. At most sixteen active plus queued writes are retained. Slots decrement only when their actual chained work settles, not when cancellation rejects the caller; a hanging native write continues to retain ownership. Focused fixtures cover exact bounds, invalid inputs, saturation, snapshot mutation, slot reuse, and saturated cancellation. Prior lifecycle and independent-review logs remain unchanged; the follow-up result is stored separately.
